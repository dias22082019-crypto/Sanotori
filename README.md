# Sanatorium OS

Мультиарендная SaaS CRM для санаториев, пансионатов и оздоровительных центров Казахстана.
Стек: React 18 + TypeScript + Vite, Tailwind CSS + shadcn/ui, Supabase (PostgreSQL, Auth, RLS), React Hook Form + Zod, i18next (ru/kk).

Архитектура и поэтапный план: см. документ «Sanatorium OS — архитектура и план» в проекте Claude.

## Быстрый старт

```bash
npm install
cp .env.example .env      # укажите URL и anon key вашего проекта Supabase
npm run dev               # http://localhost:8080
```

### Публикация на GitHub Pages

После слияния в `main` workflow `.github/workflows/pages.yml` собирает сайт и публикует его на
`https://dias22082019-crypto.github.io/Sanotori/`. Один раз включите Pages: Settings → Pages → Source: **GitHub Actions**.
В Supabase (Authentication → URL Configuration) добавьте этот адрес в Site URL и `https://dias22082019-crypto.github.io/Sanotori/**` в Redirect URLs.

### База данных

1. Создайте проект Supabase (или используйте Lovable Cloud).
2. Примените миграции по порядку из `supabase/migrations/`:
   - через Supabase CLI: `supabase link --project-ref <ref> && supabase db push`;
   - или вставьте файлы по одному в SQL Editor панели Supabase.
3. В Authentication → URL Configuration добавьте адрес сайта и redirect URL:
   `https://<ваш-домен>/onboarding`, `https://<ваш-домен>/reset-password`.
4. Включите подтверждение email (Authentication → Providers → Email → Confirm email).
5. Назначьте владельца платформы (super_admin) вручную в SQL Editor — из интерфейса это сделать нельзя намеренно:
   ```sql
   insert into public.platform_admins (user_id, note)
   select id, 'owner' from auth.users where email = 'you@example.kz';
   ```
6. Цены тарифов в `subscription_plans` по умолчанию 0 — задайте свои.

**Обновление уже установленной базы.** Если база ставилась из `supabase/setup_all.sql`, новые миграции
применяются по одной из `supabase/updates/` (каждый файл уже обёрнут в транзакцию), по порядку и один раз.
Например, для этапа 3 — `supabase/updates/20261023000005_rooms_bookings.sql`, для финансов — `supabase/updates/20261024000006_finance.sql`,
для процедур и задач — `supabase/updates/20261025000007_procedures_tasks.sql`,
для журнала и подписки — `supabase/updates/20261026000008_audit_billing.sql`.

## Проверки

```bash
npm run typecheck     # TypeScript
npm test              # unit-тесты (форматы KZT, телефоны +7, часовой пояс Asia/Almaty, схемы форм)
npm run check:i18n    # одинаковые ключи в ru.json и kk.json
npm run build         # production-сборка

# SQL-тесты RLS на чистом PostgreSQL 15+ (нужны psql и права на создание БД):
PGHOST=localhost PGPORT=5432 PGUSER=postgres ./supabase/tests/run_local.sh
```

`supabase/tests/00_supabase_shim.sql` имитирует роли и `auth.uid()` Supabase только для локального прогона —
**не применяйте его к настоящему проекту Supabase**.

SQL-тесты проверяют сценарии ТЗ: изоляцию двух санаториев (1–3), невозможность повысить роль (4),
недоступность приватных данных анониму (9), отсутствие у горничной медицинских и финансовых прав (10),
безопасные поля публичной страницы (11), ограничение изменений при истёкшей подписке (14),
а также то, что super_admin не видит сотрудников и журналы санаториев.
Этап 3 (`03_bookings_test.sql`): невозможность двойной брони при создании и переносе (5), серверный расчёт цены
с сезонами и доплатой (6), правила заезда и выезда и статусы номера (7–8), права ресепшена и горничной (10),
изоляция номеров, гостей и броней между санаториями (3), заявка с сайта без утечки данных и с антиспамом (12),
запрет новых броней при истёкшей подписке и лимит номеров тарифа (14).
Финансы (`04_finance_test.sql`): ресепшен принимает оплату, но не делает возврат и не аннулирует (13), возврат
не больше оплаченного и только с причиной, аннулированная оплата остаётся в истории и не входит в баланс,
отчёт за период сходится с оплатами, возвратами и расходами, оплаты пишутся в журнал, горничная и другой санаторий
не видят деньги (3, 10), отменённая бронь не принимает оплату, но предоплату можно вернуть, при истёкшей подписке
отчёты читаются, а запись закрыта, на тарифе Start расходов нет (14).
Процедуры и задачи (`05_procedures_tasks_test.sql`): цена и длительность из справочника, запрет пересечений кабинета,
специалиста и гостя, даты проживания, перенос (15); медсестра отмечает выполнение, но не записывает и не отменяет,
ресепшен только смотрит, горничная процедур не видит, бухгалтер видит их в счёте (10); изоляция санаториев (3);
отмена брони снимает её процедуры; исполнитель видит свои и общие задачи, берёт общую, не отменяет (16);
автоматическая уборка после выезда; при истёкшей подписке всё читается, но не меняется, на тарифе Start модулей нет (14).
Журнал и подписка (`06_audit_billing_test.sql`): изменения цен, номеров и настроек пишутся с прежним и новым
значением, по гостям — только названия полей (17); журнал видит только роль с `audit.read`, другой санаторий его
не видит, записи нельзя изменить или удалить; подписку и заявку на тариф видит только владелец, заявка работает и при
истёкшей подписке, сам себе тариф санаторий включить не может (18); владелец платформы включает тариф, не видя гостей.

## Безопасность: что важно знать

- Во фронтенде используется только публичный anon key. Права проверяют RLS и `security definer` функции в БД.
- Роли меняются только функциями `assign_member_role` / `invite_member`; прямой записи в таблицы ролей и членства нет.
- Бронирования нельзя записать в таблицу напрямую: только функциями `create_booking`, `update_booking`,
  `set_booking_status`, которые проверяют права, подписку и пересчитывают цену. Сумма с клиента не принимается.
- Оплаты, возвраты и доп. услуги пишутся только функциями `add_booking_payment`, `void_booking_payment`,
  `add_booking_extra`, `remove_booking_extra`. Ошибочная оплата аннулируется с причиной, а не удаляется; каждое действие
  попадает в `audit_logs`. Возврат требует права `refunds.create`, аннулирование — `finance.write`.
- Записи на процедуры и задачи меняются только функциями (`schedule_procedure`, `set_procedure_status`, `create_task`,
  `set_task_status` и др.); цену процедуры берёт сервер. Заметка к процедуре — служебная: диагнозы и медицинские
  сведения туда писать не нужно, для них будет отдельная медицинская карта с правом `medical.read`.
- Тариф санаторию включает только владелец платформы функцией `admin_set_plan`; санаторий может лишь отправить заявку
  (`request_plan_change`). Онлайн-оплаты подписки нет: включайте тариф только после фактической оплаты счёта.
- Изменения справочников и настроек журналируются триггером `app.audit_row_change`; значения полей гостя в журнал не копируются.
- Заявка с публичной страницы находит гостя по телефону, но не меняет его карточку и ничего не возвращает, кроме номера заявки.
- Отказ в доступе откатывает транзакцию, поэтому отклонённые попытки в `audit_logs` не пишутся —
  их видно в логах API Supabase.
- Перед запуском с реальными гостями проверьте с юристом требования Закона РК «О персональных данных и их защите»
  к месту хранения данных: облачный Supabase не размещает данные в Казахстане.
